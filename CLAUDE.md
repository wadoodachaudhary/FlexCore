## 2026-10-19 Cascading prompt groups, one-pass PromptManager decoding, conversion time limit

- **Cascading prompt groups.** A PromptGroup can hold several Prompts (a cascading list: "Model > Assembly", one LOV whose Model LOVField has the Assembly LOVField as its `Child`). `CrystalPromptManagerParser` keeps every Prompt of a group in order (FieldID + SortingType each); a parameter's prompt is the one at the `<To>` index of its `ConstraintRef xsi:type="PromptGroupConstraint"` (From..To is the cascading path, the value is chosen at To). A group of one prompt needs no index; a larger group with a missing or out-of-range index gives no list. The LOV walk now follows `Child` as well as `Field`/`Sibling` and marks LOVFields reached through a `Child` as cascading levels. A FieldID the LOV does not hold gives no list (no more fallback to the first field). A cascading level after the first gets **no** authored `<ParameterPickList>`: Crystal lists it only under the values chosen above it, and an authored list is authoritative (it would block host and dependent providers from narrowing it). It keeps its earlier list (record-selection synthesis or the host), and the conversion reports it: a `CRYSTAL_PARTIAL_EXTRACTION` diagnostic "Prompt '<name>' is a lower level of the cascading prompt group '<group>' ..." (from `ParseWarnings`, so it reaches the XML's `<ConversionDiagnostics>`). Before, every prompt of a group got the first prompt's list (the Assembly prompt offered Model codes). `CrystalReportXmlVersion.Current` is 6 (was 5) so a host re-converts XML written by the 0.1.128 converter.
- **One-pass segment decoding.** Each segment is decrypted on demand (keystream of block k = AES of ciphertext block k-1, zero at the segment start) and handed to zlib one byte per read; zlib asks for input only after using all it has and stops at its end-of-stream marker after checking the Adler-32 trailer itself, so the bytes handed out are the segment's length. The trailer is confirmed once there; the next segment's bytes are never read. Nothing is inflated twice and nothing beyond the segment is decrypted. Real reports decode to the same offsets, lengths and XML (226-RPT corpus, 216 PromptManager streams, 205 XML files: identical layouts, parameter lists and XML apart from the version stamp, except the two cascading reports' Assembly list and diagnostic). A crafted segment repeating its own trailer 200,000 times (800 KB): 41 s with the trailer search, about 0.1 s now; 16 MB: about 1.5 s.
- **Cancellation and time limit.** `CrystalRptToXml.Convert(..., CancellationToken)`, `NativeCrystalRptConverter.Convert/ReadModel(..., CancellationToken)` and `CrystalPromptManagerParser.DecodeSegments(bytes, CancellationToken)` are new overloads (the old signatures remain); `ConvertAsync` passes its token through. The token is checked between streams and subreports, per segment and every 16 decrypted bytes, and before the XML is written (a cancelled conversion writes nothing). `CrystalRptConversionOptions.Timeout` is now honoured: past it the conversion throws `TimeoutException` (zero or less: before it starts; null / `Timeout.InfiniteTimeSpan`: no limit). `RptToXmlConverter.ConversionTimeout` (default 1 minute) is passed for every conversion, so one file cannot hold the process-wide convert gate for long; hosts that treat `OperationCanceledException` as a user cancel see a timeout as an ordinary conversion failure.
- **Checks moved to the host.** `verification/CrystalPromptListChecks` now lives in the host app's `verification/` (it reads the host's installed RPTs) and references the library through `ControlKitProject` like the host's other library checks (`-p:ControlKitProject=../../../../../FlexCore/FlexCore.csproj` for FlexCore). The library keeps no `verification/` folder and no `verification/**` compile exclusion. 134 checks per library: the earlier 99 unchanged, plus the cascading reports (lists, XML, diagnostic), the crafted one-pass stream, truncated and wrong-trailer segments, cancellation and the time limit.

## 2026-10-18 Crystal prompt lists from the .rpt (PromptManager LOVs)

- The native converter now reads the whole `PromptManager` stream. It holds several XML segments stored back to back, each encrypted and zlib-compressed on its own: (1) Parameter objects (Name, ValueType, PromptGroupRef, ConstraintRef, DefaultValues), (2) PromptGroup objects (LOVDS reference, Prompt with FieldID and PickList/SortingType), (3) LOVDS objects (the LOV field tree: the value DB field plus an optional Sibling description field, each resolving through id/content-id to the first body with children that carries TableAlias and Name, plus the QueryDefinition Tables), (4) the prompt groups again in an alternate form (ignored: the first definition per ID wins). Reports without dynamic lists have three segments (no LOVDS). `CrystalPromptManagerParser` decrypts each segment from its own offset with the cipher state reset to zero (same AES-128-ECB keystream as before), and inflates it in one pass (see 2026-10-19 below; the earlier trailer search re-inflated the segment once per trailer-shaped byte run). Pinned report `Global Option Costs v1.rpt` (SHA-256 9527d5ad...1896bf95): offsets 0 / 780 / 1841 / 11406, stored lengths 780 / 1061 / 9565 / 1023, XML 2916 / 5219 / 130795 / 4809 bytes. Decoding problems degrade as before: segments after a failure are dropped silently and nothing throws out of `ApplyPromptMetadata`. `CrystalPromptManagerParser.DecodeSegments(byte[])` is public for diagnostics. Constraint -> `AllowCustomValues=false` and DefaultValues -> `InitialValues` behave exactly as before.
- Model: `CrystalParameterFieldModel.PickList` (`CrystalParameterPickListModel`: Table, ValueField, DescriptionField (null when none), Sort = Ascending | Descending | NoSort from the prompt's SortingType, default Ascending). Table is the real table name from the LOVDS QueryDefinition when the value field's alias maps to one, else the alias. A LOV on a Crystal command table (`CrystalReports.CommandTable`, e.g. PO Integration Status Report's Job Filter) yields no PickList; a description field from another table is dropped (values only).
- XML: `<ParameterFieldDefinition>` gets `<ParameterPickList Table="..." ValueField="..." DescriptionField="..." Sort="Ascending" />` right after `<ParameterInitialValues>` (DescriptionField omitted when the LOV has none). Nothing else in the XML changes.
- Loader: `<ParameterPickList>` becomes `ReportParameter.PickListSql`, one row per distinct value, sorted by value, with no DivisionID or empty-value filter (Crystal's list has none; the host drops empty values when it shows the list). With a description: `SELECT [V] AS [Value], MIN([D]) AS [Description] FROM [T] GROUP BY [V] ORDER BY [V]` (`DESC` for Descending, no ORDER BY for NoSort); without: `SELECT DISTINCT [V] AS [Value] FROM [T] ORDER BY [V]`. Identifiers are bracket-quoted with `]` doubled; a name with control characters or longer than 128 characters falls back to the previous behaviour. Precedence: explicit `<PickListSql>` > authored `<ParameterPickList>` > `SynthesizePickListSql` from the record-selection binding. `ReportParameter.PickListIsAuthored` is true only for the authored case: hosts must run that SQL as is, ahead of name-based lists and dependent pick-list providers.
- Pinned results: Community -> `SELECT [Area] AS [Value], MIN([Description]) AS [Description] FROM [tblLocality] GROUP BY [Area] ORDER BY [Area]`; Option -> `SELECT [OptionID] AS [Value], MIN([AssemblyDesc]) AS [Description] FROM [AssemblyCostsAllCommunities] GROUP BY [OptionID] ORDER BY [OptionID]`; Vendor -> `SELECT DISTINCT [Vendor_Name] AS [Value] FROM [tblVendors] ORDER BY [Vendor_Name]`; DivisionID has no LOV. They pin the report hash, the four segments, the three LOVs, the XML elements, Load/LoadPositioned SQL and flags, the precedence and refusal rules, and reports without LOVs keeping their previous PickListSql.

## 2026-10-17 Report runtime review fixes RT-1..RT-4 (FlexKit 0.1.127)
